Skill scope review, observed October 3, 2026. This is a proposed ownership and routing plan. No skill installation, profile membership, global instruction, vault instruction, plugin cache or service was changed.

The highest-value change is to stop optional profiles from reintroducing workflows that already have local owners. Keep general engineering methods discoverable across repositories. Put project facts, verification commands and local operating boundaries in the owner's AGENTS.md. Keep longer procedures in local skills or references, reached through precise task triggers.

The review covers all 82 eligible entries selected by tooling-homelab, ai-agents and product-growth, including the five shared core entries. It also examines the curated catalog's scope, the existing vault and repository installations, and three SUBCULT brand skills from the creative profile. This is not a semantic review of all 322 reservoir entries, a usage-frequency study, or a behavioral qualification of the selected procedures. Metadata and selected bodies were read; especially sensitive or overlapping procedures received deeper inspection. No past-session mining was performed.

The [82-entry matrix](2026-10-03-skill-scope-matrix.md) gives each selected entry a disposition, proposed home and reason. The [JSON snapshot](2026-10-03-skill-scope-review.json) records source paths, entrypoint hashes, structural observations and filtered profile names. Source hashes describe the observed working tree, not a committed release.

**What belongs at each scope**

| Scope | Appropriate material | Loading rule |
|---|---|---|
| Global instructions | Universal user preferences, source ownership, secret protection and required prose policy | Short instructions applied across tasks; longer supporting material stays behind pointers |
| Global curated skills | Methods useful across unrelated repositories: implementation, debugging, review, Git, verification and common language/framework work | Discoverable globally; load for the task's actual procedure |
| Optional profiles | Specialist methods, integrations and explicit commands | Activate deliberately; availability is not permission to execute or proof of compatibility |
| Repository or vault AGENTS.md | Facts and constraints that apply throughout that owner: source authority, architecture, publication boundary, required source reads and verification | Short root rules; subdirectory rules only when that directory is the relevant working scope |
| Local skill | A repeatable multi-step task with local inputs and outputs | Load when the named task occurs; root AGENTS.md can explicitly require reading an essential local procedure |
| Reference or runbook | Host inventory, API contract, long checklists and conditional operational detail | Read from the owner when the relevant branch is reached |
| Client or plugin distribution | Tool contracts, scheduler semantics, provider-specific agents and package-owned integrations | Keep the client/package owner; do not copy caches into personal skills |

Local placement provides discovery, not guaranteed execution. Codex loads skill bodies when selected. Its documented AGENTS.md instruction chain starts at the project root and walks to the working directory. A file in Work/Subcult above an independent Git repository is therefore not a dependable organization-wide instruction source. A file in a nested folder also does not automatically govern a session started at the repository root. Root pointers and fresh discovery checks must establish the intended route.

Official sources: [skill discovery](https://learn.chatgpt.com/docs/customization/overview#skills) and [AGENTS.md discovery](https://developers.openai.com/codex/guides/agents-md). Current T3 client behavior and other clients still need their own fresh-session verification.

The strongest consolidation cases are grilling into requirements-interview, handoff into session-handoff, and show-me-your-work into implementation-plan. **Verified defects and limits**

- check-agent-compatibility has invalid YAML: its unquoted description contains an internal colon. Its body also requires four named specialist agents. Parse repair and agent availability are separate qualification gates.
- The 82 selected entrypoints have no missing relative Markdown links and none exceed 500 lines. This limited check does not validate every backtick path, executable helper, external dependency or nested reference.
- Five descriptions exceed 100 words: ab-test-setup, copywriting, cursor-sdk, customer-research and page-cro. Some triggers include broad everyday phrases. Narrowing them would reduce collisions, but current runtime routing accuracy was not measured.
- Sixty-three selected entries lack agents/openai.yaml and 66 carry extra frontmatter fields. These are advisory observations. Compatibility, manual invocation, provenance and package metadata can be legitimate; do not delete them to satisfy a blanket lint rule.
- The maintenance audit helper's default roots omit the curated ~/.codex/skills base. Its ownership fallback also cannot establish OS or package ownership by itself. This review used the canonical catalog and targeted selection rather than treating default recursive cache counts as the active catalog.
- The prior managed installation verification stopped at repository-delivery-review because of installed-only Python bytecode. Its SKILL.md matched source. That failure remains separate from the current optional profile, whose prior status was clean.
- Existing dirty files and concurrent additions remain protected. At the final pre-report status check these included docs/OPERATING-MODEL.md, library/skills/patreon-manager/SKILL.md and runtime-bundles/. This report does not attribute or incorporate those additions as a completed deployment.

**Proposed migration order and verification**

1. Extend optional-profile ownership filtering to known vault-local and repository-local owners. Preserve library originals outside active selection. Check both positive local discovery and negative global discovery before retiring a name.
2. Consolidate the three clearly duplicated workflow entrypoints under their existing owners. Compare resources and invocation policy; preserve manual-only behavior where intended. Add positive and near-miss acceptance cases.
3. Add the codex-skills local maintenance procedure and adapt host workflows into Machinum's existing operations owner. Resolve stale paths, topology and script contracts before any deployment.
4. Add Switchyard development/client references and the Super Productivity diagnostic/area split. Preserve existing production-operations and gameplay boundaries.
5. Establish Studio brand and preparation routing from actual sources, with SUBCULT and product repositories pointing to the relevant owner. Reconcile current cadence/claims before deploying Patreon guidance.
6. Adapt client-specific optional workflows only for clients in actual use. Leave incompatible and another person's style entries outside the default profile.

For each change: edit the canonical source, review the diff, run the repository validator and unit tests plus relevant skill validation, preview the installer transaction, apply only reviewed scope, and verify destination hashes. Vault changes use vault-agents.py. Changes to the shared core's optional filtering must also account for Claude's explicit links and separate Blacktower distribution. Run fresh discovery from home, each target repository and each vault. Test an expected activation and a nearby task that must not activate the skill. Verify worktree discovery using the real isolated checkout; a main checkout's local skill does not prove availability in another worktree.

The first bounded implementation can consist of ownership filtering and the three duplicate consolidations. Later migrations should follow the source and behavior checks above. Changing the current core profile would not itself make this review's local routing proposals effective.
