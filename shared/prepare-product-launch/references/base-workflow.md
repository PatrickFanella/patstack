# prepare-product-launch

Use for a product's marketing packet, reusable marketing starter, or refresh of an existing packet. A single post can use the established product context directly. Repository implementation audits, visual identity creation, paid campaign operation, and publishing retain their separate workflows.

1. Read project instructions, existing marketing docs, brand ownership, product scope, and current offer. Use implementation, release, deployed behavior, and observed journeys as distinct evidence. Check registry or platform facts live when copy depends on current availability.
2. Build a compact context: audience hypotheses or actual research, reader's task, concrete product mechanism, one action/destination, voice source, and claims with dated evidence. Record disabled/planned capabilities and missing commercial facts. Do not turn a scraped product description into proof.
3. Create or revise the packet in its existing project location. Use [the starter](../assets/starter-template/README.md) only when no suitable structure exists. Typical outputs are a product brief, landing copy, short descriptions, FAQ, selected channel drafts, a real-workflow demo brief, and a campaign plan. Scale the outputs to the request.
4. Show how each substantive claim follows from a source. Keep unknowns in internal notes and remove unsupported assertions from public copy. Use customer quotes, metrics, comparisons, and media only with their actual evidence and permission.
5. Plan around available time, audience access, and an achievable first-use task. Define measures and denominators, identify missing instrumentation, and choose a review decision. A reach count is not adoption; no universal launch hour or virality promise is assumed.
6. Review the reader's full action path, placeholders, links, account/price requirements, captions, asset rights, and product voice. Run relevant documentation checks. Distinguish a written storyboard from a tested or recorded demonstration.

Return the actual saved packet, source record, checks run, and remaining verification. Preserve imported reference material separately. Drafting and syncing the files does not authorize messages, paid placements, automation, or publication. For cross-device requests, use the environment's guarded sync/deployment owner and verify each destination; do not overwrite dirty project docs.

This procedure combines this collection's original packet structure with reviewed ideas from Okara's Content Brief, Brand Voice, and Repurposing. The portable assets contain this collection's original prompts and templates. See `provenance.json`; unreviewed third-party libraries remain outside discovery.
